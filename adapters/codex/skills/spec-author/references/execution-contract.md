# 执行编排与分层读取

适用于多职责、存在依赖或需要续接的规格。帮助作者把已确定的设计交给执行者，不要求把所有工具调用写死，也不创建新的编排语言、状态机或规划层级。

## 1. 先确定每类信息放在哪里

- AGENTS.md 等适用规则保存长期纪律。作者读取这些规则，将本轮直接影响分工、权限、验证和停止的约束写入执行输入；不能假定后续执行者能访问作者的用户目录。
- SPEC 保存业务结果、原始验收、写入边界及底层能力采用决定。不同任务所需的长篇领域合同拆为独立附件，正文只保留唯一权威位置的引用。
- 独立的公共执行计划保存任务索引、依赖、共享规则、验证批次与唯一进度；各任务的完整说明分别放入任务文件，属于同一计划而非新增规划层。宿主确定后在该计划中记录实际配置。规格保留合同级验证要求，计划引用它，不手工复制测试集合。
- 独立启动单提供可直接复制的启动提示，直接列出目标、职责和禁止动作、授权、首个动作、完成与暂停边界，再按顺序指向必要规格与公共计划。历史、编写说明和资源选型理由不放在启动正文。

上述多文件结构适用于主技能第 4 节规定的整体生成或重构。文件名沿用项目约定，每个独立委派职责一份任务文件，不按命令、字段或每次重试拆文件。任务表不能代替任务文件，角色读取说明不能代替启动提示。启动单和公共计划不得把所有任务正文或领域附件列为首次必读。

只读请求只报告缺口；明确限定单文件的重构，在允许文件中保留完整启动正文、公共计划和任务章节，并说明物理分层未完成，不私自新建附件。局部修改只处理相关内容，不能声称整体重构完成。执行者不得自行把“保持最小改动”“已有未提交改动”或“仍是草稿”解释为上述例外。

合同、状态、能力采用与测试清单保持唯一来源；在启动和交接处重述少数关键执行纪律，不算另建事实源。重述必须来自适用规则或当前用户决定，保持条件和强度一致，修改原决定时同步核对相关入口；不扩展为通用规则复制或同步系统。

历史授权保留在已有历史材料中，启动单说明当次允许和禁止的动作。旧授权不能覆盖新增范围，编写时的“尚未授权”也不能否定用户后来明确发出的执行指令。调整归属后修正当前引用，不让执行者自行合并新旧安排。未授权或只读输入生成的启动单必须写明草稿不可启动实施，不得把当次限制改写成已授权写集。已授权但评审、绑定或覆盖未就绪时，启动单保留精确授权事实，同时写明相关任务不可启动及待满足条件，不重复索要授权。

## 2. 任务说明要能直接委派

每份任务文件必须包含以下内容，可以用短段或列表表达，不强制八列表格。覆盖计划中所有需要独立承接的职责，包括已有的前置事实核实、实现、审阅、发布和真实消费验证；不要为本来没有的阶段新造任务：

1. **结果与归属**：对应哪个用户结果或验收，谁是下游消费者；源文件与必要派生物分别由谁负责。
2. **启动条件**：前置合同、输入、授权、运行环境及共享资源何时满足。按依赖结果判断，不按编号或估计时间自动启动。
3. **执行配置**：职责所需的高／中／低强度、选择依据及允许调整范围。未指定宿主时不写具体模型、别名或 API 推理参数；用户指定宿主或模型后再据其有效配置细化，委派前记录实际映射。
4. **输入与披露**：启动必读、执行前必读、条件读取、默认不加载的材料；安全边界与必要合同不能降为可选。
5. **允许动作**：精确写集、禁止写集、已选公共入口、必要生成及外部权限。资料读取建议不是机械权限保证。
6. **输出与交接**：实际产物、关键证据位置、交给哪个既有任务；不能只返回总结或模型自报通过。
7. **验证安排**：既有聚焦入口、直接业务场景、生成前提、共享资源和批末门禁。沿用测试性能技能，不为任务说明另造 runner。
8. **回交条件**：何种缺口由原职责纠正，何种变化须主会话裁决或用户确认。

职责强度按任务歧义和失败代价选择，不按文件数：高强度用于复杂语义、合同或安全裁决；中强度用于边界明确的实现和集成；低强度用于机械检查、小改稿及定位。它表示所需的综合能力与推理投入，不是某个宿主的 `effort` 参数；不能把较弱模型的高推理参数直接等同于高强度职责。主会话负责范围裁决；实现职责不能同时改变验收并给自己最终批准。独立审阅的能力按适用规则确定，不把多模型投票作为默认步骤。

以下资源适配由作者在规划时判断，由主会话在委派前落实。启动单不枚举候选宿主、不解释跨平台写作原则，也不要求执行者读取另一工具的用户级规则。未指定宿主时使用通用动作和职责强度；已指定时只保留当前执行确实需要的操作。产品的宿主支持和验收另属业务合同，按相关任务读取，不因此删减。

用户未指定宿主时，模型映射保持未定；实际承接工具确定后，主会话在派发任务前依据其可见能力和适用用户规则选择模型与推理参数，记录在已有计划中。这是落实职责配置，不是重新选择业务方案或底层提供方；不需要每个宿主另写一份 SPEC，也不建立通用模型映射表。若工具缺少分派或隔离能力，不假定存在；沿既有委派方式满足职责分离，无法满足时只暂停受影响职责。

“计划使用”不等于“已生效”。由宿主已有配置或调用入口落实后记录实际可见结果。不能确认时标为未确认，不能探查隐蔽供应商路由、修改用户全局配置或私自降级。若无法确认会影响所需能力边界，只暂停该职责；不要为配置核实新建探针平台。

### 2.1 把关键纪律写成当次执行约定

同一明确范围只需一次用户授权。用户明确要求“按这份 SPEC／启动单执行”时，核对其指向的范围及限制后，直接推进已覆盖事项；不要求另说“采用第某节授权”，不逐项重复批准。只有生成、查看或评审请求时，不启动实施；文档存在或读取成功本身不产生授权。

授权核对使用用户实际指令，不把编写时的状态快照当成永久前置条件。已授权范围内的阶段推进、子任务委派、正常返修或会话续接，不再请求相同授权；交接只传递现有授权及边界，不新建批准表。用户暂停或撤回授权仍须遵守，不能用旧授权自动恢复。

只有出现尚未覆盖的目标、写集、外部动作、费用、明确保留的单独审批，或实际授权对象有歧义时，才就缺口集中确认，不重问已批准部分。系统或工具要求的审批仍须遵守，不人为叠加重复确认，也不能用“不重复授权”绕过权限限制。

启动单面向正在行动的执行者，不承担向作者解释设计方法的任务。先写目标和当前授权，再直接回答以下问题，已有短段能说清时不新增表格：

- **主会话做什么**：按适用分工写明澄清、冻结范围、委派、接口裁决、资源协调、进度和最终验收。需要职责分离的任务，明确禁止主会话接管可独立委派的成片实现；列清允许直接完成的短小核实、状态维护或既有窄集成动作。缺执行者时请求协调，不以赶工或持续目标为由自行接管。
- **下游做什么**：实现者只处理指定写集和必要自测，不能改验收、上游采用或给自己最终批准；独立审阅者按约定只读集中发现，不能一边审一边改。委派消息直接包含本职责的核心边界，不假定子会话会继承主会话的全部纪律。
- **怎样验证与回交**：重述当前任务的聚焦测试、集中审阅、统一返修和批末门禁纪律；详细选择器仍引用权威清单。说明什么错误由原职责修正、什么变化交回裁决，以及不能放宽检查的边界。
- **什么时候停**：写出缺授权、必要输入或能力不足、连续失败以及用户叫停时的动作。持续推进仅适用于已授权且前提满足的范围，不改变上述职责；未完成不能改报完成，也不能为结束检查绕过禁止动作。

没有执行者时，禁止把“不接管成片实现”改成“存在可用执行者时不接管”。保留职责分离，报告受影响任务；不得借缺人、赶工或 Goal 压力自动接管。草稿中的待决事实写明影响的任务和停止边界，不据此省略启动单，也不在生成文档时实际启动核实或实施。

关键约束用“责任人＋动作或禁止动作＋触发条件”表达，避免只写“遵守相关纪律”“灵活协调”“坚持到完成”。开头明确职责，具体决策处保留所需限制，结尾明确真实完成条件；不在每节重复同一套口号。附加规则可以补充细节，但移除不可访问的作者用户文件后，启动单仍须能约束首次动作和关键决策。

长期规则的正式来源与此次任务内重述分开：执行者仍遵守实际生效的规则；指令冲突按适用优先级处理，影响范围或权限的歧义先回交。重述不提高指令权限层级，也不保证模型遵从。需要强制限制时只使用已有权限和工具边界，不以本次文档调整为由新建 Harness。

使用 Goal 等持续执行入口时，目标必须连同核心职责、禁止动作、完成与暂停条件一起进入实际启动输入，不能只传一个成功口号或文件路径。续接或上下文压缩后，在原计划的交接位置保留当前任务、未完成项、这些仍生效的边界及下一动作；不新增常驻注入器、监控器或另一套状态文件。

## 3. 规定读取时机，不扩大上下文

按角色和阶段指定读取范围，不统一要求“启动前完整读取所有规格和报告”：

- 主会话首次启动读取适用纪律、当前目标、完整验收要求、权限、全局安全与停止边界、底层采用结论、依赖和当前状态。进入具体任务、接口裁决或最终批准前，再读该决定涉及的完整领域合同和原始证据。
- 实现职责读取自己的完整任务、直接验收、适用边界、上下游接口、所选 Skill 完整指令及必读引用，再读待改实现、直接调用方和最近测试。不默认继承整个主会话历史或其他任务的实现材料。
- 独立审阅保留全部约定验收的覆盖责任，可以在同一冻结对象上按领域读取完整合同和对应证据，再集中形成结论。分阶段读取不等于缩小审阅，也不能仅依赖实现者摘要。

每份任务文件明确启动必读、执行前必读、条件读取及默认不加载的材料；没有条件材料时明确写无。读取路径必须包含本职责适用的全局安全、授权与停止边界，再到领域合同、直接调用方和测试，不能只引用功能章节。公共计划列出所有任务文件及启动条件，执行者按当前任务选读，不要求先读完整任务集合。

区分“定位索引”与“必须读取的内容”：索引列出某文件，不自动要求整份加载；但被选合同所依赖的类型、兼容、安全与失败语义仍须完整读取。追踪这些必读引用，发现公共索引将某职责引到无关源码或全部报告时，改成具体任务入口，不把筛选责任留给执行者猜测。artifact-graph 等工具输出也须限定到当前决定需要的内容，不以“读取工具返回的全部上下文”代替读集设计。所选 Skill 明确要求的完整读取保持有效。

章节链接只用于定位，不保证局部加载。未指定执行宿主时，必须让各职责能通过整文件读取取得所需合同，拆出夹带大量无关内容的长篇领域正文；不能把范围读取留给执行时猜测。只有用户明确限定单文件，或明确选定且确认支持范围读取的执行环境，才可保留长文中的局部合同；此时须给出文件、标题起止及必需关联，先定位标题，再读取到同级或更高层标题之前，不凭旧行号截取。这不替代常规多职责交付中的独立启动单、公共计划和任务文件。

若宿主默认继承全部历史，须通过其已有方式避免继承；无法做到时说明实际负载，不能宣称已实现上下文隔离。不为读取新建提取器、合同副本或上下文管理平台。

条件读取写明触发信号，例如进入旧包兼容实现、发现真实热点、处理具体复审发现或命中架构升级条件。当前任务必需的兼容与安全合同不能等出错才读取。共享机制采用比较在规格阶段完成，执行时只加载命中能力的合同，不重新选型。

历史与当前指令混放时，将历史正文移至独立历史文件，当前入口只留必要定位；领域附件按完整语义边界组织，不把字段、异常或单个验收切成失去上下文的碎片。只迁移本轮现行输入，不为统一格式重排无关历史。

共享合同保持一份权威正文，任务文件不复制合同和进度。迁移后修正现行链接及交叉引用，保留历史授权与原验收；继续保留原版基线时，明确哪些章节仍属现行依据以及何时读取。若任务文件只是指向多份长文的索引，仍须检查传递读集，不能因任务文件变短就宣布减负。

改稿前后各顺读一次主会话启动、代表性实现和审阅路径，列清同阶段必读内容及传递引用，按实际选中内容去重比较；不是统计文件总长度就宣布减负。行数、字符数或已有词元统计仅作有范围说明的静态观察；没有实际模型运行证据，不能声称指令遵从、速度或工期已经改善。常驻纪律、附带 Skill 和源码也影响实际负载，未计入时必须说明，不制造通用上限、读集注册表或额外测试平台。

无关历史、完整日志、其他批次研究与缓存默认不加载，定位故障再读。分层披露是信息组织；有隔离需求时使用既有权限与宿主能力，不宣称 Markdown 能限制读写。

## 4. 主路径固定，例外按条件发生

固定任务依赖和汇合点、互斥写集、共享资源串行边界、必要生成责任、底层能力采用、测试策略与验收。互不依赖的只读观察可以提前，不把“最多若干执行者”当作应始终填满的配额。

允许执行者在写集和合同内调整函数实现、补读直接证据、修正编排错误。重试不要求预建节点，但必须按适用纪律处理连续失败，并保留受影响的必要复验。

追加评审只在已定义风险或用户要求出现时启动；范围、合同、安全、共享机制或权限变化回到对应权威位置裁决。相同事实不重复评审，不把动态节点扩成第二套任务树。

长程执行分别规定成功、暂停、阻塞与取消的处理。引用宿主已有停止方式，在唯一计划保留恢复点；不得为逃出完成检查而伪造成功，也不从“持续执行”推导额外权限。

## 5. 整理完成后的检查

先逐项核对实际交付物：独立启动单有可直接复制的正文，公共计划有唯一状态和全量任务索引，每个独立委派职责都有任务文件及第 2 节要求的内容。现有文件满足时直接复用；缺项则补齐，受用户明确范围限制时报告缺口。未决事实可以阻断任务就绪，但不能把缺失文档包装成“等待实施再补”。

检查每项原验收仍有人负责，任务输出能成为下游输入，没有依赖环或共享写冲突；计划与启动单没有重复维护已经移走的决定。凡是影响实现方式的未知能力，相关任务仍不可委派，只允许明确授权的事实核实。

用实际入口做一次集中冷读：暂不把作者用户目录和历史对话当作可用材料，只读启动单能否判断首个动作、主会话不能做什么、缺执行者如何处理，以及未完成但已触及权限或停止边界时怎么办？再沿必要引用检查编码职责和独立审阅，不把“文件可读、链接有效”当作执行行为已受约束。

最终答复列出实际启动入口、公共计划和任务文件索引，并简述一条实现路径与一条审阅路径的实际必读文件及补读条件。全量任务覆盖核对与代表性路径冷读在同一批次完成，不逐任务另开评审。风格、链接、制品关系或版本锁检查通过，都不能代替这项交付核对；不新建检查系统或产品测试。

若本轮生成或优化 SPEC，按 [上游能力正向匹配](capability-matching.md) 第 6 节再做一次双向覆盖核对，处置与匹配阶段相同：双向一致则继续；SPEC 单边则引导补充正文与关系并进入已有评审入口；制品单边则等待用户决定纳入、延期或认定基线未变；历史未变则保留基线；图关系成立但正文未覆盖则报告语义缺口；无图配置则说明采用缺口并引导已有入口，不虚构已检查；只读请求只报告不写。图边或 ID 能够对应，不能代替 SPEC 与相关制品正文的语义覆盖。相关未决只阻断依赖该差异的任务；无依赖任务仍可委派。文档齐全但仍有覆盖未决时，报告“文档已整理，相关任务暂不可委派”，并写明等待补充评审还是等待用户裁决。

授权同时检查三个情境：仅要求编写或评审时不实施；已明确要求按指定范围执行时不重复询问，旧的“未授权”记录不阻断；出现未覆盖动作时只确认新增缺口。不能只验证“无授权会停”，却漏掉“有授权应继续”。

已提供的规则仍按其优先级适用；冷读的缺省材料假设仅用于找出文档依赖缺口，不授权试验者忽略规则。行为推演能检查指令是否清楚，不能证明真实长程运行会遵从。只修复具体缺口，不增加形式化模型检查、自动任务编译器或多轮审阅。

## 6. 严格输出条件

必要正文、关系与适用评审未实际完成时，不编写可启动的 SPEC，也不把缺口挪到后续 T0。执行计划保持独立文件，不把完整任务进度复制进 SPEC。四项判断分开写：范围依据、正文充分性、必要关系、适用评审；每项写下实际已核实的结论和依据。必要材料、关系与评审都已完成时，已核实结论可以表示为已满足。`缺失`、`未检查`、`依据不足`、`不适用` 分别表示四种缺口，四词不是穷尽值域。独立全文审阅不受作者来源表上限约束。只缺说明或关系时补齐并复审；设计与实现冲突要报告冲突；意图不明保持待确认，不从代码反推批准需求，不倒填历史。没有真实方法时不报告闭环通过。来源索引加上本轮增量正文构成 SPEC。`HEAD` 不是未提交正文的版本。项目模板优先于默认 starter。投影字节对照不是三个宿主的真实执行。
