# 规格修改与审阅方法

吸收 OpenSpec 中已核对的五项做法。沿用本地身份、add/modify/delete 合同和已有制品入口。不引入 OpenSpec 目录结构、CLI、英文标题解析器、归档执行器或第二套工作流引擎。

## 1. 以完整需求及全部相关场景为修改单位

修改一项需求时，逐个相关场景判定：保留、改变、经批准删除，或新增。不能只用局部片段覆盖全部旧要求。

检查问题：
- 本轮声称修改的需求，其全部相关场景是否都有去向？
- 只改其中一个场景时，其他场景是显式保留还是被遗漏？
- 新增场景是否补了对应验收，而不是只改标题？

样例：一项需求有登录成功与登录失败两个场景，方案只改成功路径。必须标出失败路径是保留、同步修改还是经批准删除；不能把“已改成功路径”写成整项需求已覆盖。

## 2. 分别检查删除与重命名

删除与重命名是不同风险，不要用同一种核对。

删除：
- 旧行为现在是否仍可被用户观察到？
- 影响哪些制品、测试和承接位置？
- 删除项的历史去向写在哪里？`delete` 不能只从目录消失。

重命名：
- 旧身份与新身份能否同时定位？
- 变化只是名称，还是行为也改变了？
- 引用方是否仍指向旧身份？

沿用本地 add/modify/delete 与已有制品身份表达这些操作，不新增通用枚举或迁移引擎。

## 3. 按需求展示基线与目标差异

审阅时按需求组织简明对照：相关基线、此次目标、受影响场景。重点找出“名字未变但语义已经相反”的变化。

使用现有 Git 差异与 `artifact-graph query` / `context` / `impact` 定位材料。不新建持久化差异数据库，也不为对照新增 Markdown 解析器。

对照至少能回答：
- 基线要求用户看到什么？
- 本轮目标要求用户看到什么？
- 哪些场景证明这一差值？

## 4. 配置加载时提前诊断

图配置的结构或类型错误，应在加载时按字段路径报告。未知键给出可定位提示并保留兼容，不一律拒绝项目扩展。`extraFields` 仍是可选索引字段。已有配置必须显式写出 `allowedEdges`：缺字段给出路径和补配置方向；`[]`、`null` 或 YAML 空值采用内置默认表；非空清单完全替换默认表，按 from/to/kind 严格白名单校验，清单外报 `DISALLOWED_EDGE`。`forbiddenEdges` 仍优先。没有配置文件时保持未接入。分析关系配置时先读目标类型、关系语义和直接相关制品正文；只读请求只报告缺口并指向 `artifact-chain-bootstrap`，不改配置、不把扫描边一键放行。

表达服务配置由 `artifact-chain-setup` 调用 `scripts/setup-checks.mjs` 检查；缺项只影响表达路径。

SPEC 正文的机械检查采用当前实际安装的 Graph 包提供的 artifact.spec@1。正式发布的 Graph 0.16.0 已包含该合同，使用该正式包时按正式身份采用，不再标注候选来源；仅当使用开发候选包或显式指定候选 contracts 目录时，才需标明“候选”来源。采用前须调用 `contract explain` 获取真实 identity、revisionDigest 和 semanticMarkers，作为后续校验基础，且必须使用本次 explain 返回的 revisionDigest 执行 `contract validate-markers` 检查完整 Markdown 正文。宿主必须确认 semanticMarkers 中必需标记定义集合非空，并覆盖 changes、scope、acceptance 三项；acceptance-record 与 archive-record 为可选标记。`contract validate` 仅用于校验 JSON 实例，不得用于替代 Markdown 正文的结构化标记检查。未知合同、合同未定义必需标记、标记定义为空或正文仅含可选标记，都不能报告有效机械采用通过；若实际安装包未提供合同，明确报告缺口，禁止任何隐式回退、复制或虚称已提供。隔离消费必须基于实际安装包定位合同，不依赖父仓私有路径、个人技能或未发布 Docs 源码。所有机械检查通过后，仍须由不同职责方独立审阅完整正文与业务来源。

## 5. 识别有价值的失败样例

以下情况不能报业务通过：
- **遗漏场景**：只覆盖部分相关场景。
- **同名异义**：标题或 ID 相同，语义已相反或分裂。
- **空材料**：文件存在但没有可观察的要求或证据。
- **勾选无证据**：任务勾选、退出码 0 或模型自报完成，但没有真实行为证据。

文件存在、格式有效、复选框完成、图边成立，都不能代替语义覆盖和真实入口观察。

## 6. 严格输出条件

必要正文、关系或适用评审未完成时，不命名、不交付 SPEC，也不把补齐写成后续 T0。分别记录范围依据、正文充分性、必要关系、适用评审，并写下实际已核实的结论和依据。必要材料、关系与评审都已完成时，已核实结论可以表示为已满足。`缺失`、`未检查`、`依据不足`、`不适用` 分别表示四种缺口，四词不是穷尽值域。未创建、未引用、未入图的前置，只指向缺失附件的节点，以及依赖关系缺失，都要单独报告。沿用历史评审必须对照当前正文，变化部分另有适用评审。开发前测试规格与开发后执行结果分开。独立全文审阅不受作者来源表上限约束，并主动查找遗漏来源；它不能补签前置专业评审。只缺说明或关系时补齐并复审；实现偏离批准设计时报告冲突；意图不明保持待确认，不从代码反推批准需求，不倒填历史。没有真实方法时不报告闭环通过。SPEC 使用来源索引和本轮增量正文。`HEAD` 不是未提交正文的版本。项目已有实际模板时以项目模板为准。执行计划独立引用。
